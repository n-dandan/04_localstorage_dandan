## （1）制作アプリのタイトル
イベント抽選アプリ

## （2）制作アプリの説明（40文字程度）
ライブ等のイベント会場でグッズ抽選などを行うアプリ。

## （3）工夫した点・こだわった点
実際にイベントで使えるように抽選のシステムを実装した。
- 抽選番号の入力はライブ等のチケットのQRやバーコードを読み込めるように実装。
  - `html5-qrcode` ライブラリを使用
- 誤タップ防止
　- 誤タップで抽選画面から管理画面に遷移しないよう、誤タップ防止機能として10回タップしなければ入れないようにしてる。
   -５秒間反応がない場合はタップのカウントはリセット（あと10回に戻る）。
  - 現在は見えるようにしているが、実際は透明なボタンにする。
- 管理画面
  - イベントのイメージに合わせられるよう背景のカラーやフォントを変更できるようにしている。
  - 抽選できるチケットIDの登録や当選したIDの履歴などCSVでインポート・エクスポートできるようにしている。

## （4）難しかった点・次回トライしたいこと（または機能）
最初に何をローカルストレージに記録させるかの洗い出しと、どのデータに何を紐づけるのかの整理はAIに助けを借りながらもMECEにするのは大変だと感じた。<br>
AIと相談しつつ揉めたのが、使用済み処理について。<br>
使用済みの判定について、自分はタイムスタンプと当選結果の両方を記録させて、その２つのデータが揃っていたら使用済みで問題ないと思っていた。<br>
しかしAIは、もう一つusedの判定をつけていた。
下記の3・4行目のケースで万が一起きたときに「未使用」と判定されて2回引けてしまうより、「使用済み」として弾く方が安全という考え方だった。

usedAt(タイムスタンプ) | result | used(判定) | 状況<br>
ーーーーーーーーーーーーーーーーーーーーーーー<br>
null | null | 未使用 |まだ抽選していない<br>
あり | あり | 使用済み |正常に抽選完了<br>
あり | null | 使用済み | 処理途中でクラッシュ<br>
null | あり | 使用済み | 処理途中でクラッシュ

上記のAIの案を採用したが、設計としてusedの判定は必要なのかは、まだ自分の中で結論は出ていない。
（イベント会場でのトラブルなどを考えてどのようにすべきか？）

次回トライしたいことしてFirebase版ののイベント抽選アプリを作りたい。

## （5）備考（感想、シェアしたいこと等なんでも）
今回はローカルストレージの課題ということで、この機能を作ったが使用するシチュエーションよってこのアプリが使える使えないがあると感じた。
ローカルストレージを使っているのでネット環境でなくても使えるが、大規模イベント等で複数台のPCで抽選を使う場合などは、Firebaseなどにデータを保存する必要があると感じた。
小規模で１つのPCで抽選したり、ネット環境がないのであれば、この方式で問題ないと思う。<br>
今までの課題の中で、作っていて一番楽しかった。

## （６）制作アプリの使い方/遊び方
- 管理画面のデフォルトのパスワードは`1234`です。
- 当選商品と抽選できるチケットIDはデフォルトで管理画面に登録されています。
  - 当選商品
    - サイン入りポスター
    - チェキ
    - グッズセット
  - チケットID
    - `A-0001`-`A-0020`
    - `0001`-`0030`
- githubの`test_qr_barcode`のフォルダからダウンロードしてQRコードとバーコードを読み込ませてください。
  - 画像をスマホなどに送信して表示させてください。
  - デフォルトで登録されているIDと登録されていないID（エラー確認用）が入っています。
